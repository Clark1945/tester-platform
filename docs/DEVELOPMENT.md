# 開發文件

本文件記錄 Tester Receiver System 五個階段的開發過程。每個階段依序說明四件事：

1. **做了什麼、解決了什麼問題**
2. **在整個系統中如何運作**：從哪裡開始、到哪裡結束，以及正常流程以外會遇到哪些狀況
3. **如何驗證**：用什麼方法確認問題真的被解決，而且沒有製造新的問題
4. **留下了什麼問題、哪些沒有確認過**

設計上「為什麼這樣做」的論述在 [README.md](../README.md) 的「設計取捨」；本文件著重在過程、流程與驗證。規格在 [SPEC.md](../SPEC.md)。

所有數字都是在單機 Docker Desktop（Windows 11）上實測的結果，日期為 2026-11-15。

## 驗證方法總則

每個階段都用同一套做法，目的是區分「我認為它是對的」與「我看到它是對的」。

| 做法 | 防的是什麼 |
|---|---|
| **每階段重跑全部測試**（`go vet` + `go test -race ./...`），包含先前階段的測試 | 新程式弄壞舊功能。階段 2 改寫 API、階段 3 改寫 receiver 時，舊測試都是回歸測試 |
| **測試開著 race detector 跑** | 並行的資料競爭。這類錯誤平常不會發作，一般測試抓不到 |
| **端到端驗收以「數字對帳」為準**：送出筆數、資料庫筆數、queue 剩餘、重複筆數 | 「跑完沒有錯誤訊息」不等於正確。只有數字相符才算通過 |
| **故障情境實際製造故障**：真的 `docker stop`、`docker kill`、塞壞訊息 | 失敗處理的程式碼平常不會被執行，沒有實際觸發就等於沒測 |
| **修正後重跑原本失敗的情境，再重跑相鄰的情境** | 修 A 弄壞 B |
| **反向驗證**：故意弄壞資料，確認檢查會失敗 | 一個永遠回報通過的檢查沒有價值 |
| **以假的相依元件做單元測試**：假的 store、假的 broker 確認、假的時鐘 | 讓難以在真實環境重現的情況（連續 5 次 deadlock、panic、等一分鐘）也測得到 |

端到端驗收使用的工具：

- **k6**：純壓力，量測吞吐量與錯誤率。
- **RabbitMQ 管理 API**：讀 queue 深度、直接把訊息塞進 queue（繞過 API 的驗證）。
- **psql**：直接數資料庫筆數與重複。
- **階段 4 之後**：`simulator`、`verify`、`chaos` 三個自製工具。

一個重要的限制：管理 API 的統計數字約每 5 秒才更新一次。所有「等 queue 排空」的判斷都要連續觀察數次為 0，不能只看一次。

## 階段 1：直接寫資料庫的 API

### 做了什麼、解決了什麼問題

建立最小可用的系統：API 收到資料後直接寫進資料庫。

| 項目 | 內容 |
|---|---|
| 資料庫 | PostgreSQL + TimescaleDB，`devices` 與 `readings`（hypertable）兩張表，啟動時 seed 100 台 device |
| `internal/model` | `Reading` 的解析與驗證 |
| `internal/store` | 冪等寫入、device 檢查、查詢 |
| `cmd/api` | `POST /v1/readings`、`GET /v1/readings`、`GET /healthz`，含優雅關閉 |

**解決的核心問題：重送不重複。**

Device 收到 5xx 或逾時會重送，而且它分不出「伺服器沒收到」與「收到了但回應遺失」。所以同一筆資料一定會被送多次。這個階段確立了整個系統的冪等機制：device 產生 `uni_id` 並在重送時沿用，資料庫用 `UNIQUE (uni_id, record_time)` 擋掉第二筆。後面所有階段的重送（MQ 重新投遞、confirm 逾時後重試）都靠這同一個 constraint 吸收。

### 在系統中如何運作

**起點**：device 發出 HTTP 請求。**終點**：資料庫 commit，API 回應。

```
device ──POST──> API ──(1) 解析驗證──(2) 查 device──(3) INSERT ON CONFLICT──> 資料庫
                  │
                  └──> 202 / 400 / 404 / 503
```

**正常流程**：解析成功 → device 存在 → 寫入一筆 → 回 202。

**正常流程以外**：

| 狀況 | 系統的反應 | device 該怎麼辦 |
|---|---|---|
| JSON 壞掉、欄位缺漏、`seq < 1`、`uni_id` 不是 UUID | 400，附上原因 | 不重試（重送也一樣） |
| `record_time` 不是 UTC | 400 | 不重試 |
| body 超過 64 KiB | 413 | 不重試 |
| `device_id` 不存在 | 404 | 不重試 |
| **同一筆送第二次** | `ON CONFLICT DO NOTHING` 不新增，仍回 202 | 視為成功 |
| 資料庫連不上或逾時 | 503，訊息固定為 `service unavailable`（內部錯誤只進日誌） | 以相同的 `uni_id` / `seq` / `record_time` 重試 |
| 處理中收到 SIGTERM | 停止接受新連線，等進行中的請求完成（最多 10 秒）後結束 | 連線被拒，重試 |

兩個值得注意的細節：

- **`freq: 0` 是合法值。** Go 的整數沒有 null，欄位缺漏也會是 0。所以先解析到指標型別，是 `nil` 才代表缺漏。
- **不用「先查再寫」來去重。** 兩個並行的重送會同時查不到、同時寫入。由 constraint 把關才沒有競態。

### 如何驗證

| 驗證項目 | 方法 | 結果 |
|---|---|---|
| 驗證規則 | 17 個壞 payload 的 table-driven 測試，每個案例只弄壞一處 | 全部被拒，且錯誤都可用 `errors.Is(err, ErrInvalid)` 辨識 |
| 冪等寫入 | 對真實資料庫的整合測試：同一筆寫兩次 | 第一次 `inserted = true`、第二次 `false`，資料庫 1 筆 |
| 排序與時間範圍查詢 | 整合測試：故意不照時間順序寫入 | 回傳結果有排序，`to` 為不含 |
| HTTP 行為 | 以假的 store 測 handler：各種拒絕、store 失敗 | 狀態碼正確；503 的回應中沒有洩漏內部錯誤訊息 |
| 端到端冪等 | 同一個 `uni_id` 用 HTTP 送兩次，再用 psql 數 | 兩次都 202，資料庫 1 筆 |
| 壓力 | k6 100 VU 跑 1 分鐘 | 164,394 筆請求、0 錯誤、p95 42.65 ms；資料庫新增 164,394 筆，完全相符 |
| 優雅關閉 | `docker stop` 後看日誌與 exit code | 日誌有 `api stopped cleanly`，exit code 0 |
| 初始化 | psql 查詢 | 100 台 device、`readings` 是 hypertable |

「壓測後資料庫筆數 = 請求數」這一項同時確認了兩件事：沒有請求回了 202 卻沒寫入，也沒有寫入兩次。

### 留下的問題與未確認事項

**留下的問題（由後續階段處理）**

- **資料庫一停，API 就只能回 503。** 資料能否保住完全依賴 device 端重試。這是加入 MQ 的主要理由（階段 2）。
- **每個請求都查一次資料庫確認 device。** 階段 2 改為記憶體快取。

**未確認**

- **資料庫故障時 API 回 503 沒有端到端測過**，只有以假的 store 測過。到了階段 2，API 寫入已不經過資料庫，這條路徑不再存在。
- **優雅關閉只在沒有流量時測過**，沒有驗證「有請求正在處理時送 SIGTERM」。
- **TimescaleDB 的 chunk 區間用預設值（7 天）**，沒有調整，也沒有量測它對寫入的影響。
- **整合測試與執行中的服務共用同一個資料庫。** 測試資料用 2001 年的時間並在結束時刪除，但若測試中途被中斷會留下殘留資料。

## 階段 2：加入 RabbitMQ

### 做了什麼、解決了什麼問題

把「收資料」與「寫資料庫」拆成兩個服務，中間放 RabbitMQ。

| 項目 | 內容 |
|---|---|
| `internal/mq` publisher | 單一 goroutine 持有 amqp channel；persistent 訊息、durable queue；等 publisher confirm；斷線自動重連 |
| `internal/mq` consumer | 手動 ack、prefetch、worker pool、斷線自動重連 |
| `internal/devices` | device 名單的記憶體快取，每 30 秒從資料庫刷新 |
| `internal/retry` | 指數退避 + jitter、可被 context 取消的等待 |
| `cmd/api` | 改為發佈到 MQ，等 confirm 才回 202 |
| `cmd/receiver` | 新服務：消費、檢查 device、寫入、成功後才 ack |

**解決的問題**

- **資料庫故障時資料不丟。** 實測資料庫停機 12 秒期間，API 對 1,200 筆請求全部回 202；資料庫恢復後 1,200 筆全數寫入。階段 1 在同樣情況下只能回 503。
- **突發流量有緩衝。** API 每秒可接受約 3,700 筆，receiver 每秒寫入約 700 筆，差額堆在 queue 而不是壓垮資料庫。
- **重啟 receiver 不影響收資料。**

代價是系統多了兩個新的「可能遺失資料」的位置（API 與 broker 之間、broker 與 receiver 之間），這個階段的設計都是為了封住這兩個位置。

### 在系統中如何運作

**起點**：device 發出 HTTP 請求。**終點**：receiver ack 訊息。中間有兩次責任交接。

```
device ──POST──> API ──publish──> RabbitMQ ──deliver──> receiver ──INSERT──> 資料庫
                  │                  │                      │
          (A) 等 broker confirm   訊息落地磁碟        (B) 寫入成功後才 ack
                  │
                 202  ← 責任從 device 交給 broker
```

- **交接點 A**：API 等到 broker 確認訊息已寫入磁碟，才回 202。在那之前由 device 負責重試。
- **交接點 B**：receiver 寫入資料庫成功後才 ack。在那之前由 broker 負責保存並重新投遞。

**正常流程**：API 驗證 → 查快取 → 發佈 → 收到 confirm → 回 202；receiver 收到訊息 → 查 device → 寫入 → ack。

**正常流程以外**：

| 狀況 | 發生在哪 | 系統的反應 | 結果 |
|---|---|---|---|
| broker 斷線 | API | `Publish` 立刻回錯誤（不排隊），API 回 503；背景以退避重連 | device 重試。請求不會堆在 API 的記憶體裡 |
| confirm 逾時（2 秒）或被 nack | API | 回 503 | device 重試。**訊息可能其實已進 queue**，重試會造成重複，由資料庫擋掉 |
| 發佈時 channel 出錯 | API | 回 503，並重建整條連線 | 同上 |
| broker 重啟 | broker | durable queue + persistent 訊息，重啟後訊息仍在 | 無遺失 |
| 資料庫停機 | API | device 檢查只查記憶體快取，照常回 202 | 訊息累積在 queue |
| 資料庫停機 | receiver | 寫入失敗，稍等後把訊息放回 queue（階段 3 改為退避重試） | 資料庫恢復後補寫 |
| receiver 停機 | broker | 訊息留在 queue | receiver 啟動後消化 |
| **receiver 寫入後、ack 前掛掉** | receiver | broker 發現連線中斷，重新投遞 | 資料庫擋掉第二筆，計為 duplicate |
| receiver 收到 SIGTERM | receiver | 取消訂閱（不再收新訊息），連線保持開啟讓處理中的訊息 ack 完，再關閉 | 無遺失、無重送 |
| 快取過期：剛註冊的 device | API | 下次刷新前回 404 | 最長延遲 30 秒 |
| 快取過期：剛刪除的 device | API 放行 | receiver 的資料庫檢查擋下（階段 3 起進 DLQ） | 快取只是過濾，資料庫才是權威 |
| 快取刷新失敗 | API | 記錄警告，沿用舊名單 | 資料庫故障不影響收資料 |

**幾個關鍵的設計點**

- **單一 publisher goroutine。** amqp channel 不能被多個 goroutine 共用。只有一個 goroutine 碰它，HTTP handler 透過 Go channel 送請求。這個 goroutine 只負責「發佈」，等待 confirm 則在各個 handler 自己的 goroutine 進行，所以發佈是序列的、等待是並行的。
- **關閉的順序。** API 先停 HTTP（等進行中的請求），再停 publisher。反過來的話，正在等 confirm 的請求會失敗。
- **API 的 `/healthz` 只看 broker。** 資料庫掛掉時 API 仍然能做它的工作，不該被判定為不健康。receiver 的 `/healthz` 則兩者都看。

### 如何驗證

**單元與整合測試**

| 驗證項目 | 方法 |
|---|---|
| 並行發佈的正確性 | 對真實 broker：200 個 goroutine 同時發佈，確認每筆恰好送達一次、都是 persistent、header 完整。開著 race detector |
| 斷線時快速失敗 | publisher 未連線時 `Publish` 必須在 0.5 秒內回錯誤 |
| 發佈的內容是標準格式 | 送欄位順序不同、含多餘欄位、UUID 大寫的 payload，確認進 queue 的訊息是重新序列化後的標準格式，且 receiver 的解析函式讀得回來 |
| API 不依賴資料庫 | 假的 store 一律回錯誤，`POST` 仍須回 202 |
| receiver 的每種結局 | 假的 store 與假的 ack 介面，確認每筆訊息「恰好被處置一次」 |
| 關閉時的行為 | context 已取消時，已領到的訊息仍要寫完並 ack |
| 快取的並行安全 | 8 個 goroutine 讀、同時刷新 100 次，開著 race detector |

**端到端情境**

| 情境 | 驗證方式 | 結果 |
|---|---|---|
| 正常流量 | k6 一分鐘，等 queue 排空後比對 | 送出 223,939、資料庫 223,939、無重複 |
| receiver 停機期間送資料 | 停 receiver → 送 1,500 筆 → 確認 queue 有 1,500、資料庫 0 → 啟動 | 資料庫 1,500 |
| 消化積壓途中 SIGTERM | 堆 47,201 筆 → 啟動 receiver → 4 秒後 `docker stop` | 停止當下「已寫入 3,119 + queue 剩餘 44,082」= 47,201；重啟後 47,201，重送 0 筆 |
| broker 停機 | 停 rabbitmq 後打 API | `POST` 回 503、`/healthz` 回 503 |
| broker 重啟 | queue 內留 500 筆未消費 → 重啟 rabbitmq | 訊息仍在；API 在 broker 啟動後 8.2 秒自動重連 |
| 資料庫停機 | 停 postgres → 送 1,200 筆 | API 全部 202；receiver 14 秒內只重排 8 次（沒有 hot loop）；恢復後 1,200 筆 |

「停止當下，已寫入 + queue 剩餘 = 送出」這個等式是優雅關閉最直接的證據：每一筆訊息不是在資料庫就是在 queue，沒有第三個地方。

**事後補測（撰寫本文件時）**

以下兩項在階段 2 當時只有單元測試，後來以完整系統補測：

| 情境 | 結果 |
|---|---|
| 同一筆經 API 送 3 次（經過 MQ 的去重） | 三次都 202；資料庫 1 筆；receiver 計數器 written +1、duplicate +2 |
| **消化積壓途中對 receiver 送 SIGKILL**（無法優雅關閉） | exit code 137。當下「已寫入 6,183 + queue 剩餘 30,504」= 36,687，比送出的 36,683 多 4——那 4 筆是已寫入但來不及 ack。重啟後 broker 重新投遞，計數器顯示 duplicate = 4；最終資料庫 36,683 筆、無重複 |

SIGKILL 這一項直接示範了 at-least-once 的完整過程：ack 前掛掉 → 重新投遞 → 冪等寫入吸收。

### 留下的問題與未確認事項

**留下的問題（由階段 3 處理）**

- 永久錯誤（壞 payload、device 不存在）只是 reject 並丟棄，留下一行錯誤日誌。資料等於被靜默丟掉。
- 暫時錯誤是等 1 秒放回 queue，沒有次數上限，也不區分錯誤種類。毒訊息會永遠循環。
- worker 沒有攔截 panic。

**留下的問題（未處理）**

- **receiver 的消化速度只有 API 的五分之一左右**（700 對 3,700 筆/秒）。壓測後 queue 花了約 4 分鐘才排空。對規格的 100 msg/s 沒有影響，改善方向見 README 的「規模變成 100 倍」。
- **broker 是單節點。** 磁碟損壞會遺失尚未消費的訊息。規格把高可用列為非目標。

**未確認**

- **confirm 逾時與 broker nack 沒有端到端製造過**，只以假的 publisher 測過 API 的反應。要穩定製造「broker 收下訊息但遲遲不確認」需要網路層的故障注入工具。
- **API 啟動時資料庫不可用**會導致啟動失敗（需要載入第一份 device 名單）。這是刻意的選擇，但沒有實測過行為。
- **快取過期的兩種情況**（新增與刪除 device）只有單元測試，沒有端到端測過 30 秒的刷新週期。
- **長時間的連線中斷**（數分鐘以上）下重連的行為沒有測過，只測過 10 秒左右的停機。

## 階段 3：失敗處理與優雅關閉

### 做了什麼、解決了什麼問題

讓 receiver 的每一種失敗都有明確的去處。

| 項目 | 內容 |
|---|---|
| `internal/retry` 錯誤分類 | 依 PostgreSQL 的 SQLSTATE 與錯誤型別分成三類 |
| receiver 重試 | 在 worker 內指數退避 + jitter，可被關閉訊號中斷 |
| DLQ | `readings.dlq`，保留原始 payload，header 記錄失敗原因 |
| `internal/notify` | webhook 告警，同類告警每分鐘最多一則 |
| panic 攔截 | 每筆訊息的處理都包在 `recover()` 裡 |
| 優雅關閉 | 修正了一個關閉過慢的問題（見下文） |

**解決的問題**

- **資料不再被靜默丟棄。** 階段 2 的永久錯誤只留一行日誌。現在進 DLQ、保留原始內容、發出告警。
- **毒訊息不會卡住整條 queue。** 永久錯誤不重試；暫時錯誤最多 5 次。
- **資料庫重啟不會把訊息送進 DLQ。** 這是規格沒有涵蓋的情況，見下方「三類錯誤」。
- **一筆訊息 panic 不會讓 receiver 進入 crash loop。**

**三類錯誤**

規格只分暫時性與永久性，但照規格的預設值（100ms 起跳、最多 5 次）總共只等約 3 秒。資料庫重啟通常要 10 秒以上，所有處理中的訊息都會進 DLQ，而 chaos test 又要求 DLQ 為 0。這兩個要求互相衝突。

解法是多分出一類：

| 類別 | 判斷依據 | 處理 |
|---|---|---|
| 永久性 | payload 無法解析、device 不存在、SQLSTATE 22xxx / 23xxx / 42xxx | 不重試，進 DLQ |
| 暫時性 | deadlock（40P01）、serialization failure（40001）、statement timeout（57014）、不認得的錯誤 | 退避重試，最多 5 次，用完進 DLQ |
| 資料庫不可用 | 連線錯誤、08xxx、57P01–57P03、53xxx | 持續退避重試（上限 10 秒一次），不計次數 |

理由：資料庫連不上時問題不在訊息，換哪一筆來都會失敗，不該算在單筆訊息的重試次數上。

**逾時的歧義**：資料庫沒回應時，錯誤往往只是 `context deadline exceeded`，分不出是查詢太慢還是資料庫掛了。做法是先當成暫時性；重試用完、準備進 DLQ 前先 `Ping` 一次，Ping 也失敗就改判為資料庫不可用。也就是說，進 DLQ 的條件是「資料庫活著，但這筆就是寫不進去」。

### 在系統中如何運作

**起點**：receiver 從 queue 收到一筆訊息。**終點**：這筆訊息被 ack 或被放回 queue。

```
收到訊息
   │
   ├─ 解析失敗 ───────────────────────────────> DLQ（invalid_payload）
   │
   └─ 嘗試寫入 ◄──────────────────┐
        │                          │
        ├─ 新寫入 ──────> ack      │ 退避後重試
        ├─ 已存在 ──────> ack      │
        ├─ 永久錯誤 ────────────────┼─────────> DLQ（unknown_device / permanent_error）
        ├─ 資料庫不可用 ───────────┤（不計次數）
        └─ 暫時錯誤 ───────────────┘
              │ 已達 5 次
              ├─ Ping 成功 ────────────────────> DLQ（retries_exhausted）
              └─ Ping 失敗 ──> 改判為資料庫不可用，繼續重試

處理途中 panic ────────────────────────────────> DLQ（panic）
```

**進 DLQ 的步驟**（順序不能調換）：

1. 把原訊息發佈到 `readings.dlq`，header 帶上 `x-failure-reason`、`x-failure-detail`、`x-attempts`、`x-original-queue`、`x-failed-at`。
2. 等 broker 確認。
3. ack 原訊息。
4. 發出告警。

先 ack 再發 DLQ 的話，中間掛掉訊息就兩邊都不在了。

**訊息的所有可能結局**

| 結局 | 條件 | 訊息最後在哪 |
|---|---|---|
| ack（written） | 寫入成功 | 資料庫 |
| ack（duplicate） | 資料庫已有 | 資料庫（先前那筆） |
| ack（dlq） | 永久錯誤、重試耗盡、panic，且 DLQ 發佈成功 | `readings.dlq` |
| 放回 queue | 退避等待中收到關閉訊號 | 主 queue |
| 放回 queue | DLQ 發不出去（broker 有問題） | 主 queue，之後會再走一次流程 |
| 放回 queue | 關閉時已預取但尚未開始處理 | 主 queue |

沒有任何一條路徑是只寫日誌就讓訊息消失的。

**正常流程以外的補充**

| 狀況 | 系統的反應 |
|---|---|
| 資料庫停機很久 | worker 持續重試，每次間隔最長 10 秒。未 ack 的訊息留在 receiver 手上，其餘留在 queue |
| 重試途中收到 SIGTERM | 退避等待立刻結束，訊息放回 queue |
| 寫入途中收到 SIGTERM | 這次寫入用不受關閉訊號影響的 context，會做完（最多等一次資料庫逾時，5 秒） |
| webhook 送不出去 | 記錄錯誤後繼續，不影響訊息的處理結果 |
| 一秒內大量失敗 | 同類告警只送第一則，其餘累計；下一則會帶上 `suppressed_since_last` |
| webhook URL 沒設定 | 告警只寫日誌 |

### 如何驗證

**單元測試**（以假的 store 排定「接下來幾次要回什麼錯誤」）

| 驗證項目 | 方法 |
|---|---|
| 錯誤分類 | 19 種錯誤逐一確認分類；每一種再包兩層 `%w`，確認分類不受包裝影響 |
| 永久錯誤不重試 | 確認寫入只被呼叫 0 或 1 次，且訊息進 DLQ、原始 payload 不變 |
| 暫時錯誤重試到成功 | 連續 3 次 deadlock 後成功：寫入被呼叫 4 次、不進 DLQ |
| 重試耗盡 | 連續 20 次 deadlock：寫入**恰好**被呼叫 5 次，進 DLQ，`x-attempts = 5` |
| 資料庫不可用不計次數 | 連續 30 次「資料庫關機中」後恢復：寫入被呼叫 31 次、不進 DLQ |
| 逾時的歧義 | 連續 12 次 timeout 且 Ping 失敗：不進 DLQ |
| panic | store 直接 panic：訊息進 DLQ，panic 沒有傳出去 |
| DLQ 發不出去 | 訊息必須放回 queue、不能 ack、不發告警 |
| 關閉時不卡住 | 退避設成一分鐘，確認 context 取消後 1 秒內返回 |
| 節流 | 用假時鐘：一分鐘內 50 則只送 1 則；不同種類不互相影響；過了間隔後回報被節流的數量為 49 |
| 節流的並行安全 | 50 個 goroutine 同時告警只送出 1 則 |
| 退避的範圍 | 每個重試次數抽 200 次，確認都落在 `[d/2, d]` 且有隨機性 |

**端到端情境**

| 情境 | 驗證方式 | 結果 |
|---|---|---|
| 流量進行中資料庫停機 20 秒 | 背景持續送資料，中途 `docker stop postgres` 20 秒 | 送出 3,995、資料庫 3,995、DLQ 0。停機期間的重試日誌只有 29 行（hot loop 會是數萬行），其中 13 次被判為資料庫不可用、16 次為逾時 |
| 毒訊息 | 用管理 API 把 7 筆壞訊息直接塞進 queue（6 筆格式錯誤、1 筆未知 device），同時送 500 筆正常資料 | DLQ 恰好 7 筆，原因分別為 `invalid_payload` × 6、`unknown_device` × 1；header 完整、payload 原封不動；正常的 500 筆全數寫入 |
| webhook 節流 | 檢查 webhook 接收端的日誌 | 7 筆失敗只收到 1 則告警 |
| 消化積壓途中 SIGTERM | 同階段 2 | 1.2 秒停止、exit code 0、等式成立、重送 0 |
| 資料庫停機且 worker 重試中 SIGTERM | 停 postgres → 送資料 → `docker stop receiver` | 7.2 秒停止、exit code 0；4 個 worker 手上的訊息都還給 queue；恢復後 600 筆全數寫入 |

為什麼停機選 20 秒：預設 5 次重試只撐約 3 秒，20 秒遠超過這個範圍。如果「資料庫不可用」這一類沒有正確運作，DLQ 不會是 0。

**修正一個問題後如何確認沒有製造新問題**

第一次跑「資料庫停機時 SIGTERM」時，receiver 花了 12.6 秒才停，超過 Docker 的 10 秒寬限而被強制終止（exit code 137）。資料沒有遺失，但不是優雅關閉。

- **原因**：收到關閉訊號後，worker 仍把已預取的 50 筆逐一拿去寫入，資料庫故障時每筆都要等一次逾時。
- **修正**：關閉時尚未開始處理的訊息直接還給 queue；並把容器的停止寬限設為 20 秒。
- **確認修好**：重跑同一個情境，7.2 秒停止、exit code 0。
- **確認沒弄壞別的**：這個修改動到了關閉流程，所以另外重跑「消化積壓途中 SIGTERM」——那個情境在修改前是通過的。重跑後等式仍成立、重送仍為 0，1.2 秒內停止。全部單元測試也重跑通過。

### 留下的問題與未確認事項

**留下的問題（未處理）**

- **DLQ 沒有重放工具。** 修好問題後要從管理介面手動把訊息搬回主 queue。
- **資料庫不可用時每個 worker 各自重試**，沒有共用的 circuit breaker。4 個 worker 的規模下沒有問題。
- **沒有用 RabbitMQ 內建的 dead-letter exchange。** 由 receiver 自己發佈到 DLQ，才能附上失敗原因並在確認後才 ack。代價是 DLQ 的行為由應用程式保證，而不是 broker。

**未確認**

- **「重試耗盡進 DLQ」只有單元測試。** 要在真實資料庫上穩定製造連續 5 次 deadlock 很困難。
- **panic 攔截只有單元測試**，沒有在執行中的 receiver 上觸發過真的 panic。
- **「DLQ 發不出去」只有單元測試。**
- **webhook 接收端失敗或逾時**只有單元測試（回 500 的情況），逾時的情況沒有測。
- **預設的 1 分鐘節流間隔沒有實際跨越過**，「過了間隔後送出下一則」只用假時鐘驗證。
- **資料庫停機超過 30 分鐘**：RabbitMQ 預設會在訊息未 ack 超過 30 分鐘時關閉 channel。理論上 consumer 會自動重連、訊息重新投遞，但沒有實測。
- **錯誤分類以 PostgreSQL 文件與幾次實測為依據**，實際停機時 pgx 回傳的所有錯誤型別沒有逐一列舉過。未知的錯誤會被當成暫時性，並由 Ping 檢查兜底。

## 階段 4：驗證工具與 chaos test

### 做了什麼、解決了什麼問題

前三個階段的驗收都靠手動下指令與比對數字。這個階段把它變成可重複執行的工具，並補上「receiver 活著但不做事」的偵測。

| 項目 | 內容 |
|---|---|
| `internal/metrics` | 記憶體計數器，api 與 receiver 各有 `/metrics` |
| watchdog | receiver 內建，定期檢查三種異常並發告警 |
| `cmd/simulator` | 模擬 N 台 device，含重試與序號，結束時輸出每台的最後序號 |
| `cmd/verify` | 對帳工具，任一項失敗時 exit code 為 1 |
| `cmd/chaos` | 一鍵執行：流量 + 故障注入 + 對帳 |
| `FAULT_STALL` | 測試用的故障注入，讓 worker 拿著訊息不處理 |

**解決的問題**

- **「有沒有掉資料」可以被證明，而不只是相信。** 每筆資料帶一個每台 device 各自遞增的 `seq`，事後檢查序號是否連續完整。
- **驗收可以一鍵重跑。** 之後改任何程式，跑一次 chaos test 就知道可靠性有沒有被弄壞。
- **consumer 卡住能被發現。** `/healthz` 只能回答「行程還在、連線還在」，看不出「沒在做事」。

### 在系統中如何運作

這個階段的元件大多在系統**外面**觀察系統，而不是在資料路徑上。

**simulator**

**起點**：啟動。**終點**：輸出報告。

每台 device 一個 goroutine，依序送出資料：前一筆收到 202 才送下一筆。所以回報 `last_seq = 60` 就代表 1 到 60 全部被 API 接受了。

| 狀況 | simulator 的反應 |
|---|---|
| 202 | 記為 accepted，`last_seq` 前進 |
| 5xx、逾時、連線失敗 | 退避後以**完全相同的 body** 重送 |
| 4xx | 不重試，記為 rejected（正常情況應為 0；有的話 simulator 以非 0 結束） |
| 時間到了，但手上那筆還沒確認 | 繼續重試一段時間（預設 60 秒），讓 `last_seq` 準確 |
| 重試到逾時仍未確認 | 記為 unconfirmed。這筆可能其實已進系統，verify 對該 device 容許多出一筆 |
| Ctrl+C | 停止產生新資料，仍會輸出報告 |

**verify**

**起點**：讀入 simulator 的報告。**終點**：exit code。

依序做五項檢查，一項失敗不會中斷後面的檢查，一次看到全部差異：

| 檢查 | 抓得到什麼 |
|---|---|
| queue 排空、DLQ 為 0 | 還有資料在路上，或有資料被放棄 |
| 序號缺口 | 中間掉了一筆 |
| 每台 device 的 `max(seq)` = 報告的最後序號 | **尾端遺失**——缺口查詢看不到的盲點 |
| 總筆數 = API 接受的筆數 | 前兩項的交叉確認 |
| `(uni_id, record_time)` 與 `(device_id, seq)` 都無重複 | 冪等失效 |

另有第六項計數器恆等式：`-strict` 時是硬性檢查，否則只列出數字。

exit code：0 通過、1 檢查沒過、2 工具本身無法執行（連不上資料庫等）。

**chaos**

**起點**：`docker compose --profile tools run --rm chaos`。**終點**：exit code。

```
前置檢查（服務健康、Docker socket 可用）
   → 清空 readings 與兩個 queue
   → 啟動 simulator（背景）
   → 停 receiver 10 秒 → 啟動
   → 停 postgres 10 秒 → 啟動
   → （選配）重啟 rabbitmq
   → 等 simulator 結束
   → 等服務恢復健康
   → verify（等 queue 排空後對帳）
```

| 狀況 | chaos 的反應 |
|---|---|
| 服務不健康或 Docker socket 不可用 | 在開始前就失敗（exit code 2），不會跑到一半 |
| 流量時間太短、排不進三次故障 | 啟動時拒絕執行 |
| 故障注入途中出錯 | 嘗試把三個服務都啟動回來，再回報錯誤 |
| 停機等待途中被 Ctrl+C | 仍會把該服務啟動回來 |

**watchdog**

在 receiver 行程內，每分鐘檢查一次：

| 告警 | 條件 |
|---|---|
| `dlq_not_empty` | `readings.dlq` 深度 > 0 |
| `consumer_stuck` | 等待中的訊息比上一輪多，且這段期間一筆都沒處理完 |
| `no_writes` | 超過 2 分鐘沒有成功寫入，且 queue 不是空的 |

| 狀況 | watchdog 的反應 |
|---|---|
| 沒有流量、很久沒寫入 | 不告警（queue 是空的） |
| queue 很長而且在變長，但持續有在寫入 | 不告警（只是忙） |
| 剛啟動、從未寫入過 | 以啟動時間為基準，前 2 分鐘不告警 |
| 第一次檢查 | 沒有上一輪可比較，不判斷 `consumer_stuck` |
| 管理 API 查不到 | 記錄警告、這一輪不判斷，不假裝正常也不亂告警 |
| 沒設定管理 API 的位址 | watchdog 停用，啟動時記錄警告 |

「有沒有處理完」用 receiver 自己的計數器判斷，而不是管理 API 的 ack rate，因為後者有約 5 秒的延遲。

### 如何驗證

**單元測試**

| 驗證項目 | 方法 |
|---|---|
| simulator 的序號連續 | 假的 API 記下每個請求，確認每台 device 收到的序號是 1、2、3… |
| **重送的內容完全相同** | 假的 API 前 3 次回 503，確認 4 次請求的 body 一字不差 |
| 4xx 不重試 | 假的 API 一律回 404，確認請求數 = rejected 數 |
| 放棄未確認的資料 | 假的 API 一律回 503，確認在時限內結束、每台恰好 1 筆 unconfirmed |
| verify 抓得到每一種問題 | 從一個「完全正確」的情境出發，每個測試只弄壞一處，共 9 種：中間缺口、尾端遺失、device 整個不見、多出未知 device、筆數太少、筆數太多、`(device_id, seq)` 重複、queue 未排空、DLQ 非空 |
| unconfirmed 的容許範圍 | 那一筆「有寫入」與「沒寫入」兩種情況都要通過 |
| 恆等式的兩種模式 | 平衡時通過；不平衡時 `-strict` 失敗、一般模式只列為資訊 |
| watchdog 的每個條件 | 假的 queue 深度與假時鐘：健康但忙碌不告警、空閒不告警、三種告警各自觸發、恢復後停止告警 |
| 計數器的並行安全 | 50 個 goroutine 各累加 100 次，結果必須恰好 5,000 |
| 計數器與訊息結局一致 | 處理一系列訊息後，`written + duplicate + dlq + requeued` 必須等於 `received` |

**端到端情境**

| 情境 | 結果 |
|---|---|
| Chaos test（100 台、60 秒，停 receiver 10 秒、停 postgres 10 秒） | 6,000 筆被接受；五項檢查全過；exit code 0 |
| Chaos 完整版（90 秒，另外重啟 RabbitMQ） | 7,611 筆被接受，simulator 重試 778 次；五項檢查全過；exit code 0 |
| 穩態跑 20 秒，`verify -strict` | accepted 2,000 = written 2,000 + duplicate 0 + dlq 0 + queue 0 |
| consumer 卡住 | `/healthz` 仍回 200、資料庫 0 筆；收到 `consumer_stuck` 與 `no_writes` 各一則；解除後 3,000 筆全數補寫 |

**反向驗證：確認 verify 不是永遠回報通過**

chaos 通過之後，手動從資料庫刪掉 3 筆再跑 verify：

- 刪掉 `device-007` 的最後 2 筆（尾端遺失）
- 刪掉 `device-042` 的第 10 筆（中間缺口）

結果：

```
[FAIL] sequence gaps          1 missing, e.g. device-042#10
[FAIL] last seq per device    1 devices differ:
         device-007: db max=74, simulator last=76 (lost 2)
[FAIL] row count              7608 rows, expected 7611 (difference -3)
RESULT: FAILED
```

exit code 1。這裡有一個值得注意的細節：缺口查詢只回報了 1 筆。`device-007` 掉的 2 筆在尾端，缺口查詢完全看不到，是「最後序號」那項抓到的。這正是需要兩種檢查的原因。

**consumer 卡住的驗證為什麼有說服力**

卡住期間 receiver 的 `/healthz` 回 200、計數器全部為 0、資料庫 0 筆。也就是說，如果只靠健康檢查，這個故障完全不會被發現。watchdog 是從「queue 在長、卻沒有東西被處理完」這個結果發現的。解除故障後再跑 verify，3,000 筆全數補寫，確認故障注入本身沒有造成遺失。

**chaos test 作為回歸測試**

chaos test 同時重跑了階段 2 與階段 3 的主要情境（receiver 停機、資料庫停機、broker 重啟），而且是在流量進行中、依序發生。階段 4 新增的計數器動到了 api 與 receiver 的處理流程，chaos 通過就代表這些修改沒有弄壞先前的保證。

### 留下的問題與未確認事項

**留下的問題（未處理）**

- **計數器恆等式在服務重啟後不成立。** 計數器在記憶體裡，重啟歸零；重新投遞會被重複計為 duplicate。chaos 實測左邊 6,000、右邊 5,247。因此 chaos 以資料庫為準，恆等式只在穩態下作為硬性檢查。要讓它跨重啟成立需要持久化計數。
- **watchdog 在 receiver 行程內。** receiver 整個掛掉時它也跟著消失，那種情況要靠外部監控。
- **chaos 需要掛載 Docker socket**，等同給該容器主機的 Docker 控制權，只適合本機測試。
- **simulator 沒有「送壞訊息」的功能。** 壞訊息會被 API 以 400 擋下，到不了 queue。驗證 DLQ 要用管理 API 直接塞訊息。
- **verify 假設 `readings` 只有這一次執行的資料**，所以 chaos 開跑前會清空資料表。不能對有既有資料的資料庫使用。

**未確認**

- **watchdog 只用縮短的間隔驗證過**（檢查間隔 5 秒、閾值 10 秒）。預設的 1 分鐘與 2 分鐘沒有實際等過，只以假時鐘測過。
- **`dlq_not_empty` 告警沒有端到端觸發過。** 階段 3 驗證 DLQ 時 watchdog 還不存在；階段 4 的卡住測試只觸發了另外兩種。它只有單元測試。
- **unconfirmed 的路徑沒有端到端出現過。** 所有執行的 unconfirmed 都是 0。
- **`-strict` 模式只在「沒有任何重送」的情況下測過。** 有 confirm 逾時造成重複時恆等式會差多少，沒有實測。
- **chaos 只在 Windows 的 Docker Desktop 上跑過。** Linux 與 macOS 上 Docker socket 的權限行為可能不同。
- **chaos 的故障是依序發生的。** 沒有測過同時發生（例如資料庫與 broker 一起停）或更長的停機。
- **長時間執行沒有測過。** 最長的一次是 90 秒。記憶體是否穩定、連線是否會洩漏，沒有資料。

## 追加：Prometheus 與 Grafana

規格把監控堆疊列為非目標；這是五個階段完成後追加的需求（2026-11-16）。

### 做了什麼、解決了什麼問題

| 項目 | 內容 |
|---|---|
| `internal/metrics` | 加上 Prometheus 格式的輸出與延遲 histogram；原有的 atomic 計數器不變 |
| api、receiver | `/metrics` 改為 Prometheus 格式；原本的 JSON 移到 `/metrics.json` |
| `monitoring/prometheus.yml` | 每 5 秒抓取 api、receiver、RabbitMQ |
| `monitoring/alerts.yml` | 六條告警規則 |
| `monitoring/grafana/` | 自動載入的資料來源與一個儀表板（14 個面板） |
| compose | 新增 `prometheus`（9090）與 `grafana`（3001） |

**解決的問題**

- **看得到趨勢。** 原本的計數器只有當下的累計值。現在可以看到「receiver 停機時 queue 上升、恢復後下降」的過程。
- **看得到延遲的分布**，而不只是筆數。
- **receiver 整個掛掉時有告警。** 這是 watchdog 的盲點（它跑在 receiver 行程內）。
- **計數器重啟歸零不再影響圖表。** `rate()` 會自動處理重置。

### 在系統中如何運作

監控在資料路徑之外，只讀不寫。

```
api ──────/metrics──┐
receiver ─/metrics──┼──< Prometheus（每 5 秒抓取、評估告警規則）<── Grafana（查詢並繪圖）
RabbitMQ ─/metrics/detailed─┘
```

**起點**：Prometheus 每 5 秒向三個目標發出 HTTP 請求。**終點**：資料存進 Prometheus，Grafana 查詢時讀出。

計數器的讀取路徑：api 與 receiver 處理資料時累加 atomic 變數（和之前一樣）；Prometheus 來抓取的那一刻才讀取這些變數。所以 `/metrics`、`/metrics.json` 與 watchdog 看到的是同一個數字，不會不一致。

**正常流程以外**：

| 狀況 | 反應 |
|---|---|
| receiver 或 api 停機 | 抓取失敗，`up` 變成 0；30 秒後 `ReceiverDown` / `ApiDown` 觸發 |
| receiver 重啟，計數器歸零 | `rate()` 偵測到數值變小，當成重置處理，圖表不會出現負值或斷崖 |
| RabbitMQ 重啟 | 該次抓取失敗，圖上有短暫的缺口；恢復後繼續 |
| Prometheus 停機 | api 與 receiver 完全不受影響（它們不知道有沒有人來抓）。停機期間的資料不會補回來 |
| Grafana 停機 | 不影響抓取與告警規則的評估 |
| 從未寫入過 | 「距離上次寫入」面板顯示「尚未寫入」，而不是一個很大的數字 |

### 如何驗證

| 驗證項目 | 方法 | 結果 |
|---|---|---|
| 輸出格式正確 | 單元測試：記錄幾筆後檢查 Prometheus 輸出的每一行，包含 histogram 的 bucket | 通過 |
| 兩種輸出一致 | 單元測試 + 實際比對 `/metrics` 與 `/metrics.json` | chaos 之後兩邊都是 accepted 7,960、written 6,443、duplicate 2、retried 20 |
| 零值仍可用 | 單元測試：沒有 registry 的計數器不能 panic | 通過 |
| 抓取目標 | 查詢 Prometheus 的 targets API | 三個目標都是 `up`，沒有錯誤 |
| 告警規則語法 | 查詢 rules API | 六條都是 `health=ok` |
| RabbitMQ 的指標名稱 | 寫設定時是依文件推測的，啟動後向 Prometheus 查詢實際存在的名稱 | 與設定相符 |
| **沒有弄壞原本的保證** | 這次改動了 api 與 receiver 記錄指標的每一個位置，所以重跑完整版 chaos test | 7,960 筆、五項檢查全過、exit code 0 |
| 圖表反映實際發生的事 | 查詢 chaos 期間的資料 | queue 最高 1,353、unacked 最高 50（等於 prefetch）、`up` 在 receiver 與 RabbitMQ 停機時降為 0、api 始終為 1 |
| `ReceiverDown` 告警 | 停掉 receiver，輪詢 alerts API | 10 秒進入 pending、40 秒 firing；重啟後解除 |
| 儀表板 | 用瀏覽器打開並截圖；另向 Grafana 的 API 確認載入狀態，並直接向 Prometheus 查詢各面板使用的運算式 | 14 個面板載入成功；上方 10 個面板在瀏覽器中確認有畫出 chaos 期間的資料、主控台沒有錯誤；下方 4 個面板（延遲、goroutine、記憶體）以查詢確認運算式有資料，沒有在瀏覽器中看過畫出來的樣子 |

chaos 期間 unacked 的最大值恰好是 50，等於 prefetch 的設定值。這是從另一個角度確認了 prefetch 有生效。

### 留下的問題與未確認事項

**留下的問題**

- **告警規則沒有接 Alertmanager**，不會主動通知，只能在 Prometheus 的頁面上看到。主動通知仍靠 watchdog。
- **沒有 PostgreSQL 的指標。**
- **Go 版本從 1.25 升到 1.26**，因為 Prometheus 的 client 套件要求。建置用的映像檔已跟著更新。
- **本機沒有 C 編譯器時跑不了 race detector。** 要用 `$env:GO_IN_DOCKER='1'` 讓腳本改在容器裡跑。

**未確認**

- **六條告警規則只實際觸發過 `ReceiverDown` 一條。** 其餘五條只確認語法正確、載入成功。

- **儀表板下方 4 個面板沒有在瀏覽器中看過實際畫面**，只確認了運算式查得到資料（goroutine：api 14、receiver 23；記憶體各約 25 MB；p99 延遲約 21–25 毫秒）。
- **長時間的資料保留沒有測過。** 設定保留 7 天，實際只累積了幾分鐘的資料。
- **告警說明文字是中文**，在 Prometheus 的頁面上是否正常顯示沒有用瀏覽器確認（用 PowerShell 讀出來是亂碼，推測是 PowerShell 的編碼問題）。

| 保證 | 證據 |
